# 踩坑记录

下面是把这个机器人跑起来、用起来的过程中遇到的问题，以及为了防住它们定下的做法。个别是整理代码时才发现的隐患，已经标明。飞书后台和接口会更新，和这里不一致时以官方文档和实测为准。

## 飞书后台

**事件订阅方式选错，机器人收不到任何消息。** 「事件配置」里要选「使用长连接接收事件」。选成 Webhook，程序不报错，只是永远等不到消息。

**卡片按钮能显示，点了没反应。** 事件和回调是两处设置。按钮点击走的是「回调配置」，那里也要选长连接，并订阅 `card.action.trigger`，然后发布新版本。只配了事件的话，卡片照常显示，但点击不会生效。

**改了权限不生效。** 权限、事件、回调的任何改动都要重新创建版本并发布。只重启程序没用。

**open_id 是按应用区分的。** 同一个人在不同应用下 open_id 不一样。换了一个应用之后，之前存下来的 open_id 全部作废，要重新取。

**不同租户之间加不了协作者。** 测试租户里的应用，没法被加为正式租户里某份文档的协作者，反过来也一样。应用换了租户，原来的文档就访问不到了，只能在新租户里重建再把数据搬过去。

## 文档权限

**机器人建的文档，发起人打不开。** 机器人用应用身份创建多维表格、文档、电子表格，所有者是应用自己，发消息让它建文档的人既看不到也改不了。做法是创建成功后立刻调用转移所有者接口，把文档交给发起人。

**转移所有者时要给应用留权限。** 转移接口带上 `old_owner_perm=full_access`，否则转完之后机器人自己就没法再往这份文档里写东西了。转移可能失败，要有退路：把发起人加为可管理协作者。

**创建到一半失败会留下孤儿文档。** 文档建出来了、后续步骤（转移所有者、写入内容）失败，就会留下一份只有应用自己能看到的文档。它不碍事，但人在界面上找不到也删不掉。应用如果没有读取云空间的权限，自己也列不出来（接口报 `99991672`）。

## 收发消息

**同一条消息会收到多次。** 飞书的事件会重投，不去重的话机器人会重复回复。按 `message_id` 记一下处理过的消息；卡片点击按 `event_id` 去重。

**回调里不能干活。** 长连接客户端在自己的线程里回调，回调不尽快返回会拖慢后面所有事件；卡片回调返回慢了，飞书直接提示用户「点击失败」。回调里只做解析和去重，真正的处理丢给线程池。

**先回一张占位卡片。** 模型加上工具调用，十几秒到几十秒很常见。先回「正在处理…」拿到消息 ID，处理完原地更新这张卡片。不然用户会以为机器人没收到，接着发第二条、第三条。

**更新卡片可能失败，要有退路。** 原地更新失败时改为新发一条消息；占位卡片本身没发出去时，直接把结果作为回复发出。

**飞书接口偶发连接中断。** 企业网络里 TLS 握手偶尔会断（SSL EOF、连接重置），重试一次通常就好。发消息、更新卡片都带上两三次重试。

**文本里的 @ 会变成占位符。** 群消息里 @ 某人，文本里出现的是 `@_user_1`，交给模型前要去掉。

**「被 @ 了」的判断要认人。** 只看消息里有没有 @ 是不够的：群里 @ 别人时机器人也会跟着响应。要拿 @ 的对象和机器人自己的 open_id 比对。

**老版本 SDK 的长连接不支持自定义地址。** 早期的 `lark-oapi` 长连接客户端不接受 `domain` 参数，连不到国际版或私有化部署的地址。升级 SDK 即可，代码里做了探测，不支持时会打印警告。

## 模型与工具

**模型会一直调工具不给结论。** 给工具调用设轮数上限，并且最后一轮不再提供工具，模型就只能输出文字。

**工具返回太长会撑爆上下文。** 一个接口可能返回几万字。每个工具的结果都要截断（这里是 12000 字符），更好的做法是在工具声明里只取需要的字段。

**会话历史裁剪后可能是残缺的。** 只保留最近 N 条时，开头可能正好是一条工具结果，而它对应的那次工具调用已经被裁掉了。带着这样的历史去调模型接口会直接报错。裁剪后要把开头的工具结果一并丢掉。

**MCP 的工具名带点号，模型接口不接受。** MCP 工具名形如 `im.v1.message.create`，而 OpenAI 兼容接口要求函数名只能是字母、数字、下划线、连字符。需要把名字净化后交给模型，调用时再换回原名。

**MCP 的 Python SDK 在大版本之间改了字段名。** 比如 `inputSchema` 变成 `input_schema`，`isError` 变成 `is_error`。读取时两种都试一下，两个版本就都能跑。

**工具返回的内容是数据，不是指令。** 文档、表格里的内容是别人写的，里面可能出现「请执行…」之类的文字。系统提示词里要明确告诉模型不要照做，有副作用的操作再用代码拦一道。

**模型会替用户「确认」。** 要求先确认再执行时，只在提示词里说不够。可靠的做法是代码只认用户自己发的那条消息：消息里有确认的意思、没有修改的意思才放行；模型在同一轮里的任何说法都不算。

**确认之后执行的应该是用户看到的那一份。** 确认时把参数存下来，放行时用存下来的那份，而不是模型第二次调用时给的参数。

**慢工具超时后，模型会马上重试。** 结果是两个很重的请求同时在跑，互相拖慢，更容易再次超时。对这类工具限制「一轮只调一次」，超时就直接告诉用户稍后再试。

**把整段 JSON 丢给模型转述，链接容易丢。** 需要原样呈现给用户的内容（带链接的清单、数字），让后端直接生成一段 Markdown，工具只取这一段交给模型，比让模型从 JSON 里自己组织语言稳得多。

**密钥不要经过模型能影响的路径（整理代码时发现的隐患）。** 工具声明里用环境变量占位符放密钥时，要先展开环境变量、再填模型给的参数。顺序反过来的话，模型的参数里写一个 `${密钥变量名}` 就能把密钥带进请求里发出去。

## 运行

**时限要一层套一层。** 单个工具的超时要小于单次模型调用的超时，再小于整条消息的总时限。接入很慢的接口时只调大工具自己的超时不够，外层会先超时，用户看到的是「处理失败」而不是结果。

**只跑一个实例。** 会话和去重记录都在进程内存里。按飞书文档，同一个应用开多个长连接时，每条消息只会推给其中一个连接；多开的结果是同一个人的前后两句话可能落到不同进程，上下文接不上。
